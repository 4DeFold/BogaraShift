# BogaraShift — planning prototype

A trilingual (RU/KK/EN) Next.js prototype for selecting outlines and preparing seasonal field plans. It is **not** a cadastral, agronomic or NASA product. It has local drafts and an optional authenticated cloud copy, not the full Farm workspace described in the implementation specification.

```sh
npm ci
npm run dev   # http://localhost:3000/selectmap
npm test
npm run build
```

## What works now

- `/selectmap`: Automatic NASA CMR/GIBS HLS S30/L30 imagery selection for the map centre; draw/edit a new outline manually. There are no date or satellite selectors and no RGB contour algorithm. A user may separately confirm a valid outline after reviewing it. Confirmation is not cadastral verification. Legacy selection cells remain draft and are labelled as such.
- `/fieldplan`: one Leaflet map with Canvas, viewport filtering, low-zoom groups and capped labels; paginated cards use schematic SVG outlines rather than maps. Search, crop filters and season selection are local. Synthetic browser testing with 300 fields verified one map and 50 cards per page, not a real-world performance guarantee.
- Polygon and MultiPolygon GeoJSON import (including holes), with coordinate, topology, size and vertex checks. Imported records start as drafts. Import allows up to 500 features / 2 MiB and 2,000 vertices per feature; antimeridian polygons and coordinates beyond ±85° latitude are not supported. Export GeoJSON, CSV for the selected season, printable field summary, and a JSON backup/restore are available. GeoJSON carries boundaries and names only. Protect JSON backups: they include all observations and attachments. Restore replaces local data after confirmation.
- Local geodesic area uses Turf and is an **approximation**. After loading from the cloud the server-calculated PostGIS geography area is shown, unless the local geometry has changed. Neither value is a surveyed area. Grid cells are excluded from economic totals; unknown areas do not become zero-area fields. Draft/unconfirmed outlines are included as approximate areas and identified as drafts.
- The planning screen shows one preliminary rotation option, not a validated suitability recommendation: wheat as the preceding crop leads to a chickpea option, and chickpea leads to winter wheat. Known standing water or salinity and known recent chickpea history prevent a choice; missing history and other predecessors do not get a guessed option. Missing information, herbicide residues and suitability must be reviewed with an agronomist; no soil report or NASA data is used for this rule. It is not a regional agronomic model, comprehensive ranking or yield prediction. The option is saved only on explicit acceptance; manual changes remain possible. The interface uses the existing season plan A, while old B/C data is retained, visible read-only if present and included in backups. Occupancy dates are entered manually and the economic tool uses user assumptions, not a forecast. A soil report and its crop remain separate from the planned crop and local to the browser.
- `/fieldplan` includes an optional Supabase email/password account and private farm. Local edits remain local until explicitly uploaded. Download replaces the local field list after a warning; export the JSON backup first. Upload upserts matching IDs but deliberately does not delete remote fields. Attachments are excluded from the cloud and cannot be restored from it. A revision check rejects conflicting saves, and the cloud snapshot returns fields and revision atomically. An existing cloud farm must first be loaded on a new device before upload is allowed; export the local JSON backup first. Restoring a JSON backup clears the local sync marker, so load the current cloud snapshot before saving to an existing farm again. Up to 500 fields are supported per farm. Local data is shared by accounts using the same browser profile; signing out does not erase it. PostGIS validates geometries, calculates server area and preserves geometry versions; RLS restricts reads to farm members. Account invitation, shared editing UI and cloud deletion are not implemented.
- NASA POWER is requested automatically when opening a field detail or changing its selected season; no load button is required. The browser sends a rounded grid coordinate to a fixed server endpoint; upstream requests use Next.js's 24-hour fetch cache where supported by the hosting platform. Only precipitation and daily maximum temperature are requested. Missing values are not zero; coverage is shown and gaps break dry spells. POWER is regional modelled context, not a field measurement. POWER requires no API key. The sandbox cannot reach NASA services, so real upstream responses and GIBS tiles must be verified in the deployed environment.

Rotation background (not local validation): [ICRISAT chickpea agronomy](https://oar.icrisat.org/8535/1/LegumPerspectives_3_29-32_2014.pdf) and [MSU Extension chickpea production](https://apps.msuextension.org/montguide/guide.html?sku=MT201703AG). These sources discuss cereal rotations and constraints; they do not validate this rule for southern Kazakhstan.

## Separate demonstration

Open `/demo/selectmap` or `/demo/fieldplan` directly. There are intentionally no links to these pages from the working UI. The demo starts with ten fictional fields, outlines, soil-analysis values, previous crops and plans. The numbered cells can be selected on the map; clearing the demo list allows the examples to be added again with their data already filled in. Reset restores the original ten. Demo data and language are stored under separate browser keys; operations in the demo do not alter working fields or the cloud sync marker.

The numeric values, boundaries, report files, climate and explanation in the demo are invented, not real laboratory results, NASA climate data or AI output. They must not be used for farming decisions. The demonstration does not require a BogaraShift account and sends no AI or climate API calls; map imagery may still request NASA GIBS tiles. The Vercel preview remains protected by Vercel login at the user's request.

## Storage and limitations

Fields, plans, observations and optional PDF/JPG/PNG attachments (up to 1 MiB each) are stored in this browser's localStorage. They are not synced automatically, encrypted, backed up automatically, or protected from other users of the same browser. Only an explicit upload sends a copy of fields and observations to the selected authenticated Supabase farm; attachments are never uploaded. Browser clearing or device loss deletes them. The JSON backup can include sensitive location and soil data; store it securely. Saving reports as local data URLs is legacy behavior, not a private Supabase Storage implementation.

Not yet implemented: automatic or offline sync, member invitation/management, private file storage, FTW jobs/worker or precomputed FTW dataset, satellite-band processing and NDVI, full agronomic rules engine, analysis of uploaded reports by AI, merge/split, or the full API and E2E/security suite from the specification. The POWER endpoint is a public prototype proxy, not production-grade: a shared platform-wide rate limiter (the in-memory throttle is per instance only), durable cache/observability, authentication and provider availability monitoring are still needed before production. No keys are stored in this repository or in the browser.

## Satellite imagery

The map uses open NASA GIBS HLS imagery via WMTS, without a NASA token. The app chooses between `HLS_S30_Nadir_BRDF_Adjusted_Reflectance` (Sentinel-2) and `HLS_L30_Nadir_BRDF_Adjusted_Reflectance` (Landsat) automatically. Source products have a 30 m grid; GIBS Web Mercator level 12 is the highest native level and further zoom enlarges pixels. Coverage is not global on every day. [NASA HLS](https://www.earthdata.nasa.gov/data/catalog/lpcloud-hlss30-2.0) · [NASA POWER](https://power.larc.nasa.gov/docs/) · [GIBS](https://www.earthdata.nasa.gov/data/imagery/global-imagery-browse-services-gibs).

Imagery selection searches both HLS products at the map centre in 2025, filters out granules with missing or over 10% cloud metadata, prioritizes lower granule cloud cover, then May–September and newer dates, and checks up to 30 candidate days, then checks the centre pixel of each GIBS tile for transparency; a 404 is treated as missing coverage, while network failures stop the search instead of silently selecting older data. The date is UTC; cloud estimates apply to whole granules, and neither this estimate nor an opaque pixel guarantees a cloud-free field or coverage elsewhere on the map. This is not a cloud-masked, region-wide mosaic. The user's browser sends the map centre to NASA CMR and requests tiles directly from GIBS. If nothing is found or the services cannot be reached, the map clearly reports this; manual outlines remain available. This prototype requires a real browser/network test against NASA. Native HLS data is 30 m, while the Web Mercator GIBS display is resampled at native max zoom 12. The welcome image is an AI-generated illustration, not satellite imagery.

## Cloud preview setup

The preview branch uses branch-scoped Vercel environment variables `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, and `NEXT_PUBLIC_SUPABASE_AUTH_REDIRECT_URL`. Only the public key is used by the browser, under Postgres RLS; no service-role key is used by this application. The provided Supabase project must have the migrations in `supabase/migrations` applied. Registration requires email confirmation; the default Supabase mailer has testing limits. The confirmation URL is restricted to the branch preview (and local development). The current Vercel preview may itself require Vercel login.

The database tests were run in rolled-back transactions using two temporary synthetic users: farm isolation, unauthorized RPCs, revision conflicts, geometry versioning, server area and omission of report attachments were checked. This is not a substitute for a production security audit or an end-to-end signup/email test. No real NASA or Supabase browser traffic was verified from the sandbox.

The reproducible database isolation check is in `tests/sql/rls_workspace.sql`; run it as a privileged database operator on a disposable/test project. It creates temporary auth users inside a rolled-back transaction.

## Optional AI preview

Any visitor can explicitly request an informational Google Gemini explanation without signing in, based on the preliminary crop option, harvest year, previous crop and predefined observation codes. The interface lists the exact data sent for each answer, including unknown fields. Field names, coordinates, uploaded soil reports, their contents and NASA data are **not** sent. This is not a laboratory analysis, an agronomic recommendation or a substitute for professional advice. The user is warned before requesting it.

The server route is disabled until the `ai_quota` and `anonymous_ai_quota` migrations are applied and a server-only `GEMINI_API_KEY` is configured in the preview hosting environment. Do not use a `NEXT_PUBLIC_` variable, commit a key, put it in a URL, or expose it to the browser. The default model is `gemini-3.5-flash-lite`; `GEMINI_MODEL` can be changed to a compatible generateContent model. For Gemini 3.5 Flash-Lite, the thinking level is minimal and the output limit is 2048 tokens including thinking. If explicitly configured to Gemini 2.5 Flash, thinking is disabled; Google restricts 2.5 access for new projects. No provider fallback is attempted. Truncated or blocked responses are not presented as complete. Models can be retired, unavailable, restricted or incur charges. Google may use submitted data to improve products on the free tier; check current provider terms before deployment.

Database reservations serialize across instances and cap the application at three logical requests per hashed proxy IP and 30 per project per UTC day (shared with older authenticated calls). Raw IP addresses are not stored; only a server-keyed hash is stored (rotating the Gemini key changes the per-IP bucket while the global limit remains); records older than seven days are pruned when a subsequent reservation occurs. Users behind one proxy may share the same cap, and an unrecognised proxy address falls into one common bucket. Each reservation makes at most one provider call. Failed calls consume a reservation, deliberately bounding retries and spend. A short per-instance cooldown applies after 429. The cap cannot constrain other applications using the same key or guarantee a provider balance, and is not a substitute for Google account spending limits, shared WAF/rate-limiting, monitoring or an external security review. The public reservation RPC can be called directly and an attacker can exhaust the daily quota even without making paid calls; a protected server-only reservation credential or a WAF is required for production. The app fails closed when shared quota storage is unavailable. `tests/sql/ai_quota.sql` and `tests/sql/anonymous_ai_quota.sql` are rolled-back functional checks for quotas and access privileges on a disposable database; a separate rolled-back check also verified the 30-request global cap on the preview database. The AI response and prompt are not persisted by this app; the external provider handles data under its own policies. Local planning and NASA context do not depend on AI.
